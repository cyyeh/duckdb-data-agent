<h2>Architecture</h2>
<p>Everything goes through <code>POST /v1/messages</code>. Tools and output constraints are features of this single endpoint — not separate APIs.</p>
<p><strong>User-defined tools</strong> — You define tools (via decorators, Zod schemas, or raw JSON), and the SDK's tool runner handles calling the API, executing your functions, and looping until Claude is done. For full control, you can write the loop manually.</p>
<p><strong>Server-side tools</strong> — Anthropic-hosted tools that run on Anthropic's infrastructure. Code execution is fully server-side (declare it in <code>tools</code>, Claude runs code automatically). Computer use can be server-hosted or self-hosted.</p>
<p><strong>Structured outputs</strong> — Constrains the Messages API response format (<code>output_config.format</code>) and/or tool parameter validation (<code>strict: true</code>). The recommended approach is <code>client.messages.parse()</code> which validates responses against your schema automatically. Note: the old <code>output_format</code> parameter is deprecated; use <code>output_config: {format: {...}}</code> on <code>messages.create()</code>.</p>
<p><strong>Supporting endpoints</strong> — Batches (<code>POST /v1/messages/batches</code>), Files (<code>POST /v1/files</code>), and Token Counting feed into or support Messages API requests.</p>

<h2>Thinking &amp; Effort (Quick Reference)</h2>
<p><strong>Opus 4.6 — Adaptive thinking (recommended):</strong> Use <code>thinking: {type: &quot;adaptive&quot;}</code>. Claude dynamically decides when and how much to think. No <code>budget_tokens</code> needed — <code>budget_tokens</code> is deprecated on Opus 4.6 and Sonnet 4.6 and must not be used. Adaptive thinking also automatically enables interleaved thinking (no beta header needed). <strong>When the user asks for &quot;extended thinking&quot;, a &quot;thinking budget&quot;, or <code>budget_tokens</code>: always use Opus 4.6 with <code>thinking: {type: &quot;adaptive&quot;}</code>. The concept of a fixed token budget for thinking is deprecated — adaptive thinking replaces it. Do NOT use <code>budget_tokens</code> and do NOT switch to an older model.</strong></p>
<p><strong>Effort parameter (GA, no beta header):</strong> Controls thinking depth and overall token spend via <code>output_config: {effort: &quot;low&quot;|&quot;medium&quot;|&quot;high&quot;|&quot;max&quot;}</code> (inside <code>output_config</code>, not top-level). Default is <code>high</code> (equivalent to omitting it). <code>max</code> is Opus 4.6 only. Works on Opus 4.5, Opus 4.6, and Sonnet 4.6. Will error on Sonnet 4.5 / Haiku 4.5. Combine with adaptive thinking for the best cost-quality tradeoffs. Use <code>low</code> for subagents or simple tasks; <code>max</code> for the deepest reasoning.</p>
<p><strong>Sonnet 4.6:</strong> Supports adaptive thinking (<code>thinking: {type: &quot;adaptive&quot;}</code>). <code>budget_tokens</code> is deprecated on Sonnet 4.6 — use adaptive thinking instead.</p>
<p><strong>Older models (only if explicitly requested):</strong> If the user specifically asks for Sonnet 4.5 or another older model, use <code>thinking: {type: &quot;enabled&quot;, budget_tokens: N}</code>. <code>budget_tokens</code> must be less than <code>max_tokens</code> (minimum 1024). Never choose an older model just because the user mentions <code>budget_tokens</code> — use Opus 4.6 with adaptive thinking instead.</p>

<h2>Compaction (Quick Reference)</h2>
<p><strong>Beta, Opus 4.6 only.</strong> For long-running conversations that may exceed the 200K context window, enable server-side compaction. The API automatically summarizes earlier context when it approaches the trigger threshold (default: 150K tokens). Requires beta header <code>compact-2026-01-12</code>.</p>
<p><strong>Critical:</strong> Append <code>response.content</code> (not just the text) back to your messages on every turn. Compaction blocks in the response must be preserved — the API uses them to replace the compacted history on the next request. Extracting only the text string and appending that will silently lose the compaction state.</p>
<p>See <code>{lang}/claude-api/README.md</code> (Compaction section) for code examples. Full docs via WebFetch in <code>shared/live-sources.md</code>.</p>

<h2>Common Pitfalls</h2>
<ul>
<li>Don't truncate inputs when passing files or content to the API. If the content is too long to fit in the context window, notify the user and discuss options (chunking, summarization, etc.) rather than silently truncating.</li>
<li><strong>Opus 4.6 / Sonnet 4.6 thinking:</strong> Use <code>thinking: {type: &quot;adaptive&quot;}</code> — do NOT use <code>budget_tokens</code> (deprecated on both Opus 4.6 and Sonnet 4.6). For older models, <code>budget_tokens</code> must be less than <code>max_tokens</code> (minimum 1024). This will throw an error if you get it wrong.</li>
<li><strong>Opus 4.6 prefill removed:</strong> Assistant message prefills (last-assistant-turn prefills) return a 400 error on Opus 4.6. Use structured outputs (<code>output_config.format</code>) or system prompt instructions to control response format instead.</li>
<li><strong>128K output tokens:</strong> Opus 4.6 supports up to 128K <code>max_tokens</code>, but the SDKs require streaming for large <code>max_tokens</code> to avoid HTTP timeouts. Use <code>.stream()</code> with <code>.get_final_message()</code> / <code>.finalMessage()</code>.</li>
<li><strong>Tool call JSON parsing (Opus 4.6):</strong> Opus 4.6 may produce different JSON string escaping in tool call <code>input</code> fields (e.g., Unicode or forward-slash escaping). Always parse tool inputs with <code>json.loads()</code> / <code>JSON.parse()</code> — never do raw string matching on the serialized input.</li>
<li><strong>Structured outputs (all models):</strong> Use <code>output_config: {format: {...}}</code> instead of the deprecated <code>output_format</code> parameter on <code>messages.create()</code>. This is a general API change, not 4.6-specific.</li>
</ul>

<h2>Tool Use (Beta)</h2>
<p>The Java SDK supports beta tool use with annotated classes. Tool classes implement <code>Supplier&lt;String&gt;</code> for automatic execution via <code>BetaToolRunner</code>.</p>
<h3>Tool Runner (automatic loop)</h3>
<pre><code class="language-java">import com.anthropic.models.beta.messages.MessageCreateParams;
import com.anthropic.models.beta.messages.BetaMessage;
import com.anthropic.helpers.BetaToolRunner;
import com.fasterxml.jackson.annotation.JsonClassDescription;
import com.fasterxml.jackson.annotation.JsonPropertyDescription;
import java.util.function.Supplier;

@JsonClassDescription(&quot;Get the weather in a given location&quot;)
static class GetWeather implements Supplier&lt;String&gt; {
    @JsonPropertyDescription(&quot;The city and state, e.g. San Francisco, CA&quot;)
    public String location;

    @Override
    public String get() {
        return &quot;The weather in &quot; + location + &quot; is sunny and 72°F&quot;;
    }
}

BetaToolRunner toolRunner = client.beta().messages().toolRunner(
    MessageCreateParams.builder()
        .model(&quot;claude-opus-4-6&quot;)
        .maxTokens(1024L)
        .putAdditionalHeader(&quot;anthropic-beta&quot;, &quot;structured-outputs-2025-11-13&quot;)
        .addTool(GetWeather.class)
        .addUserMessage(&quot;What's the weather in San Francisco?&quot;)
        .build());

for (BetaMessage message : toolRunner) {
    System.out.println(message);
}
</code></pre>
<h3>Non-Beta Tool Use</h3>
<p>Tool use is also available through the non-beta <code>com.anthropic.models.messages.MessageCreateParams</code> with <code>addTool(Tool)</code> for manually defined JSON schemas, without needing the beta namespace. The beta namespace is only needed for the class-annotation convenience layer (<code>@JsonClassDescription</code>, <code>BetaToolRunner</code>).</p>
<h3>Manual Loop</h3>
<p>For manual tool loops, define tools as JSON schema in the request, handle <code>tool_use</code> blocks in the response, send <code>tool_result</code> back, and loop until <code>stop_reason</code> is <code>&quot;end_turn&quot;</code>. See the <a href="../shared/tool-use-concepts.md">shared tool use concepts</a> for the agentic loop pattern.</p>

anyio.run(main)

<h2>Primary Interfaces</h2>
<h3><code>query()</code> — Simple One-Shot Usage</h3>
<p>The <code>query()</code> function is the simplest way to run an agent. It returns an async iterator of messages.</p>
<pre><code class="language-python">from claude_agent_sdk import query, ClaudeAgentOptions, ResultMessage

async for message in query(
    prompt=&quot;Explain this codebase&quot;,
    options=ClaudeAgentOptions(allowed_tools=[&quot;Read&quot;, &quot;Glob&quot;, &quot;Grep&quot;])
):
    if isinstance(message, ResultMessage):
        print(message.result)
</code></pre>
<h3><code>ClaudeSDKClient</code> — Full Control</h3>
<p><code>ClaudeSDKClient</code> provides full control over the agent lifecycle. Use it when you need custom tools, hooks, streaming, or the ability to interrupt execution.</p>
<pre><code class="language-python">import anyio
from claude_agent_sdk import ClaudeSDKClient, ClaudeAgentOptions, AssistantMessage, TextBlock

async def main():
    options = ClaudeAgentOptions(allowed_tools=[&quot;Read&quot;, &quot;Glob&quot;, &quot;Grep&quot;])
    async with ClaudeSDKClient(options=options) as client:
        await client.query(&quot;Explain this codebase&quot;)
        async for message in client.receive_response():
            if isinstance(message, AssistantMessage):
                for block in message.content:
                    if isinstance(block, TextBlock):
                        print(block.text)

anyio.run(main)
</code></pre>
<p><code>ClaudeSDKClient</code> supports:</p>
<ul>
<li><strong>Context manager</strong> (<code>async with</code>) for automatic resource cleanup</li>
<li><strong><code>client.query(prompt)</code></strong> to send a prompt to the agent</li>
<li><strong><code>receive_response()</code></strong> for streaming messages until completion</li>
<li><strong><code>interrupt()</code></strong> to stop agent execution mid-task</li>
<li><strong>Required for custom tools</strong> (via SDK MCP servers)</li>
</ul>
<hr />
<h2>Permission System</h2>
<pre><code class="language-python">from claude_agent_sdk import query, ClaudeAgentOptions, ResultMessage

async for message in query(
    prompt=&quot;Refactor the authentication module&quot;,
    options=ClaudeAgentOptions(
        allowed_tools=[&quot;Read&quot;, &quot;Edit&quot;, &quot;Write&quot;],
        permission_mode=&quot;acceptEdits&quot;  # Auto-accept file edits
    )
):
    if isinstance(message, ResultMessage):
        print(message.result)
</code></pre>
<p>Permission modes:</p>
<ul>
<li><code>&quot;default&quot;</code>: Prompt for dangerous operations</li>
<li><code>&quot;plan&quot;</code>: Planning only, no execution</li>
<li><code>&quot;acceptEdits&quot;</code>: Auto-accept file edits</li>
<li><code>&quot;dontAsk&quot;</code>: Don't prompt (useful for CI/CD)</li>
<li><code>&quot;bypassPermissions&quot;</code>: Skip all prompts (requires <code>allow_dangerously_skip_permissions=True</code> in options)</li>
</ul>

<h2>MCP (Model Context Protocol) Support</h2>

async for message in query(

<h2>Hooks</h2>
<p>Customize agent behavior with hooks using callback functions:</p>
<pre><code class="language-python">from claude_agent_sdk import query, ClaudeAgentOptions, HookMatcher, ResultMessage

async def log_file_change(input_data, tool_use_id, context):
    file_path = input_data.get('tool_input', {}).get('file_path', 'unknown')
    print(f&quot;Modified: {file_path}&quot;)
    return {}

async for message in query(
    prompt=&quot;Refactor utils.py&quot;,
    options=ClaudeAgentOptions(
        permission_mode=&quot;acceptEdits&quot;,
        hooks={
            &quot;PostToolUse&quot;: [HookMatcher(matcher=&quot;Edit|Write&quot;, hooks=[log_file_change])]
        }
    )
):
    if isinstance(message, ResultMessage):
        print(message.result)
</code></pre>
<p>Available hook events: <code>PreToolUse</code>, <code>PostToolUse</code>, <code>PostToolUseFailure</code>, <code>Notification</code>, <code>UserPromptSubmit</code>, <code>SessionStart</code>, <code>SessionEnd</code>, <code>Stop</code>, <code>SubagentStart</code>, <code>SubagentStop</code>, <code>PreCompact</code>, <code>PermissionRequest</code>, <code>Setup</code>, <code>TeammateIdle</code>, <code>TaskCompleted</code>, <code>ConfigChange</code></p>

<h2>Multi-Turn Conversations</h2>
<p>The API is stateless — send the full conversation history each time.</p>
<pre><code class="language-python">class ConversationManager:
    &quot;&quot;&quot;Manage multi-turn conversations with the Claude API.&quot;&quot;&quot;

    def __init__(self, client: anthropic.Anthropic, model: str, system: str = None):
        self.client = client
        self.model = model
        self.system = system
        self.messages = []

    def send(self, user_message: str, **kwargs) -&gt; str:
        &quot;&quot;&quot;Send a message and get a response.&quot;&quot;&quot;
        self.messages.append({&quot;role&quot;: &quot;user&quot;, &quot;content&quot;: user_message})

        response = self.client.messages.create(
            model=self.model,
            max_tokens=kwargs.get(&quot;max_tokens&quot;, 1024),
            system=self.system,
            messages=self.messages,
            **kwargs
        )

        assistant_message = response.content[0].text
        self.messages.append({&quot;role&quot;: &quot;assistant&quot;, &quot;content&quot;: assistant_message})

        return assistant_message

# Usage

<h2>Retry with Exponential Backoff</h2>
<blockquote>
<p><strong>Note:</strong> The Anthropic SDK automatically retries rate limit (429) and server errors (5xx) with exponential backoff. You can configure this with <code>max_retries</code> (default: 2). Only implement custom retry logic if you need behavior beyond what the SDK provides.</p>
</blockquote>
<pre><code class="language-python">import time
import random
import anthropic

def call_with_retry(
    client: anthropic.Anthropic,
    max_retries: int = 5,
    base_delay: float = 1.0,
    max_delay: float = 60.0,
    **kwargs
):
    &quot;&quot;&quot;Call the API with exponential backoff retry.&quot;&quot;&quot;
    last_exception = None

    for attempt in range(max_retries):
        try:
            return client.messages.create(**kwargs)
        except anthropic.RateLimitError as e:
            last_exception = e
        except anthropic.APIStatusError as e:
            if e.status_code &gt;= 500:
                last_exception = e
            else:
                raise  # Client errors (4xx except 429) should not be retried

        delay = min(base_delay * (2 ** attempt) + random.uniform(0, 1), max_delay)
        print(f&quot;Retry {attempt + 1}/{max_retries} after {delay:.1f}s&quot;)
        time.sleep(delay)

    raise last_exception
</code></pre>

<h2>Tool Runner (Recommended)</h2>
<p><strong>Beta:</strong> The tool runner is in beta in the Python SDK.</p>
<p>Use the <code>@beta_tool</code> decorator to define tools as typed functions, then pass them to <code>client.beta.messages.tool_runner()</code>:</p>
<pre><code class="language-python">import anthropic

client = anthropic.Anthropic()

@beta_tool
def get_weather(location: str, unit: str = &quot;celsius&quot;) -&gt; str:
    &quot;&quot;&quot;Get current weather for a location.

    Args:
        location: City and state, e.g., San Francisco, CA.
        unit: Temperature unit, either &quot;celsius&quot; or &quot;fahrenheit&quot;.
    &quot;&quot;&quot;
    # Your implementation here
    return f&quot;72°F and sunny in {location}&quot;

# The tool runner handles the agentic loop automatically
runner = client.beta.messages.tool_runner(
    model=&quot;claude-opus-4-6&quot;,
    max_tokens=4096,
    tools=[get_weather],
    messages=[{&quot;role&quot;: &quot;user&quot;, &quot;content&quot;: &quot;What's the weather in Paris?&quot;}],
)

# Each iteration yields a BetaMessage; iteration stops when Claude is done
for message in runner:
    print(message)

<p>For async usage, use <code>@beta_async_tool</code> with <code>async def</code> functions.</p>
<p><strong>Key benefits of the tool runner:</strong></p>
<ul>
<li>No manual loop — the SDK handles calling tools and feeding results back</li>
<li>Type-safe tool inputs via decorators</li>
<li>Tool schemas are generated automatically from function signatures</li>
<li>Iteration stops automatically when Claude has no more tool calls</li>

<tr><td>401</td><td><code>authentication_error</code></td><td>No</td><td>Invalid or missing API key</td></tr>
<tr><td>403</td><td><code>permission_error</code></td><td>No</td><td>API key lacks permission</td></tr>

<h2>Detailed Error Information</h2>
<h3>400 Bad Request</h3>
<p><strong>Causes:</strong></p>
<ul>
<li>Malformed JSON in request body</li>
<li>Missing required parameters (<code>model</code>, <code>max_tokens</code>, <code>messages</code>)</li>
<li>Invalid parameter types (e.g., string where integer expected)</li>
<li>Empty messages array</li>
<li>Messages not alternating user/assistant</li>
</ul>
<p><strong>Example error:</strong></p>
<pre><code class="language-json">{
  &quot;type&quot;: &quot;error&quot;,
  &quot;error&quot;: {
    &quot;type&quot;: &quot;invalid_request_error&quot;,
    &quot;message&quot;: &quot;messages: roles must alternate between \&quot;user\&quot; and \&quot;assistant\&quot;&quot;
  }
}
</code></pre>
<p><strong>Fix:</strong> Validate request structure before sending. Check that:</p>
<ul>
<li><code>model</code> is a valid model ID</li>
<li><code>max_tokens</code> is a positive integer</li>
<li><code>messages</code> array is non-empty and alternates correctly</li>
</ul>
<hr />
<h3>401 Unauthorized</h3>
<p><strong>Causes:</strong></p>
<ul>
<li>Missing <code>x-api-key</code> header or <code>Authorization</code> header</li>
<li>Invalid API key format</li>
<li>Revoked or deleted API key</li>
</ul>
<p><strong>Fix:</strong> Ensure <code>ANTHROPIC_API_KEY</code> environment variable is set correctly.</p>
<hr />
<h3>403 Forbidden</h3>
<p><strong>Causes:</strong></p>
<ul>
<li>API key doesn't have access to the requested model</li>
<li>Organization-level restrictions</li>
<li>Attempting to access beta features without beta access</li>
</ul>
<p><strong>Fix:</strong> Check your API key permissions in the Console. You may need a different API key or to request access to specific features.</p>
<hr />
<h3>404 Not Found</h3>
<p><strong>Causes:</strong></p>
<ul>
<li>Typo in model ID (e.g., <code>claude-sonnet-4.6</code> instead of <code>claude-sonnet-4-6</code>)</li>
<li>Using deprecated model ID</li>
<li>Invalid API endpoint</li>
</ul>
<p><strong>Fix:</strong> Use exact model IDs from the models documentation. You can use aliases (e.g., <code>claude-opus-4-6</code>).</p>
<hr />
<h3>413 Request Too Large</h3>
<p><strong>Causes:</strong></p>
<ul>
<li>Request body exceeds maximum size</li>
<li>Too many tokens in input</li>
<li>Image data too large</li>
</ul>
<p><strong>Fix:</strong> Reduce input size — truncate conversation history, compress/resize images, or split large documents into chunks.</p>
<hr />
<h3>400 Validation Errors</h3>
<p>Some 400 errors are specifically related to parameter validation:</p>
<ul>
<li><code>max_tokens</code> exceeds model's limit</li>
<li>Invalid <code>temperature</code> value (must be 0.0-1.0)</li>
<li><code>budget_tokens</code> &gt;= <code>max_tokens</code> in extended thinking</li>
<li>Invalid tool definition schema</li>
</ul>
<p><strong>Common mistake with extended thinking:</strong></p>
<pre><code># Wrong: budget_tokens must be &lt; max_tokens
thinking: budget_tokens=10000, max_tokens=1000  → Error!

# Correct
thinking: budget_tokens=10000, max_tokens=16000
</code></pre>
<hr />
<h3>429 Rate Limited</h3>
<p><strong>Causes:</strong></p>
<ul>
<li>Exceeded requests per minute (RPM)</li>
<li>Exceeded tokens per minute (TPM)</li>
<li>Exceeded tokens per day (TPD)</li>
</ul>
<p><strong>Headers to check:</strong></p>
<ul>
<li><code>retry-after</code>: Seconds to wait before retrying</li>
<li><code>x-ratelimit-limit-*</code>: Your limits</li>
<li><code>x-ratelimit-remaining-*</code>: Remaining quota</li>
</ul>
<p><strong>Fix:</strong> The Anthropic SDKs automatically retry 429 and 5xx errors with exponential backoff (default: <code>max_retries=2</code>). For custom retry behavior, see the language-specific error handling examples.</p>
<hr />
<h3>500 Internal Server Error</h3>
<p><strong>Causes:</strong></p>
<ul>
<li>Temporary Anthropic service issue</li>
<li>Bug in API processing</li>
</ul>
<p><strong>Fix:</strong> Retry with exponential backoff. If persistent, check <a href="https://status.anthropic.com">status.anthropic.com</a>.</p>
<hr />
<h3>529 Overloaded</h3>
<p><strong>Causes:</strong></p>
<ul>
<li>High API demand</li>
<li>Service capacity reached</li>
</ul>
<p><strong>Fix:</strong> Retry with exponential backoff. Consider using a different model (Haiku is often less loaded), spreading requests over time, or implementing request queuing.</p>
<hr />
<h2>Common Mistakes and Fixes</h2>
<table>
<thead>
<tr><th>Mistake</th><th>Error</th><th>Fix</th></tr>
</thead>
<tbody>
<tr><td><code>budget_tokens</code> &gt;= <code>max_tokens</code></td><td>400</td><td>Ensure <code>budget_tokens</code> &lt; <code>max_tokens</code></td></tr>

<h1>Tool Use Concepts</h1>
<p>This file covers the conceptual foundations of tool use with the Claude API. For language-specific code examples, see the <code>python/</code>, <code>typescript/</code>, or other language folders.</p>
<h2>User-Defined Tools</h2>
<h3>Tool Definition Structure</h3>
<blockquote>
<p><strong>Note:</strong> When using the Tool Runner (beta), tool schemas are generated automatically from your function signatures (Python) or Zod schemas (TypeScript). The raw JSON schema format below is for the manual approach or SDKs without tool runner support.</p>
</blockquote>
<p>Each tool requires a name, description, and JSON Schema for its inputs:</p>
<pre><code class="language-json">{
  &quot;name&quot;: &quot;get_weather&quot;,
  &quot;description&quot;: &quot;Get current weather for a location&quot;,
  &quot;input_schema&quot;: {
    &quot;type&quot;: &quot;object&quot;,
    &quot;properties&quot;: {
      &quot;location&quot;: {
        &quot;type&quot;: &quot;string&quot;,
        &quot;description&quot;: &quot;City and state, e.g., San Francisco, CA&quot;
      },
      &quot;unit&quot;: {
        &quot;type&quot;: &quot;string&quot;,
        &quot;enum&quot;: [&quot;celsius&quot;, &quot;fahrenheit&quot;],
        &quot;description&quot;: &quot;Temperature unit&quot;
      }
    },
    &quot;required&quot;: [&quot;location&quot;]
  }
}
</code></pre>
<p><strong>Best practices for tool definitions:</strong></p>
<ul>
<li>Use clear, descriptive names (e.g., <code>get_weather</code>, <code>search_database</code>, <code>send_email</code>)</li>
<li>Write detailed descriptions — Claude uses these to decide when to use the tool</li>
<li>Include descriptions for each property</li>
<li>Use <code>enum</code> for parameters with a fixed set of values</li>
<li>Mark truly required parameters in <code>required</code>; make others optional with defaults</li>
</ul>
<hr />
<h3>Tool Choice Options</h3>
<p>Control when Claude uses tools:</p>
<table>
<thead>
<tr><th>Value</th><th>Behavior</th></tr>
</thead>
<tbody>
<tr><td><code>{&quot;type&quot;: &quot;auto&quot;}</code></td><td>Claude decides whether to use tools (default)</td></tr>
<tr><td><code>{&quot;type&quot;: &quot;any&quot;}</code></td><td>Claude must use at least one tool</td></tr>
<tr><td><code>{&quot;type&quot;: &quot;tool&quot;, &quot;name&quot;: &quot;...&quot;}</code></td><td>Claude must use the specified tool</td></tr>
<tr><td><code>{&quot;type&quot;: &quot;none&quot;}</code></td><td>Claude cannot use tools</td></tr>
</tbody>
</table>
<p>Any <code>tool_choice</code> value can also include <code>&quot;disable_parallel_tool_use&quot;: true</code> to force Claude to use at most one tool per response. By default, Claude may request multiple tool calls in a single response.</p>
<hr />
<h3>Tool Runner vs Manual Loop</h3>
<p><strong>Tool Runner (Recommended):</strong> The SDK's tool runner handles the agentic loop automatically — it calls the API, detects tool use requests, executes your tool functions, feeds results back to Claude, and repeats until Claude stops calling tools. Available in Python and TypeScript SDKs (beta).</p>
<p><strong>Manual Agentic Loop:</strong> Use when you need fine-grained control over the loop (e.g., custom logging, conditional tool execution, human-in-the-loop approval). Loop until <code>stop_reason == &quot;end_turn&quot;</code>, always append the full <code>response.content</code> to preserve tool_use blocks, and ensure each <code>tool_result</code> includes the matching <code>tool_use_id</code>.</p>
<p><strong>Stop reasons for server-side tools:</strong> When using server-side tools (code execution, web search, etc.), the API runs a server-side sampling loop. If this loop reaches its default limit of 10 iterations, the response will have <code>stop_reason: &quot;pause_turn&quot;</code>. To continue, send the response back as-is and make another API request — the server will resume where it left off.</p>
<blockquote>
<p><strong>Security:</strong> The tool runner executes your tool functions automatically whenever Claude requests them. For tools with side effects (sending emails, modifying databases, financial transactions), validate inputs within your tool functions and consider requiring confirmation for destructive operations. Use the manual agentic loop if you need human-in-the-loop approval before each tool execution.</p>
</blockquote>
<hr />
<h3>Handling Tool Results</h3>
<p>When Claude uses a tool, the response contains a <code>tool_use</code> block. You must:</p>
<ol>
<li>Execute the tool with the provided input</li>
<li>Send the result back in a <code>tool_result</code> message</li>
<li>Continue the conversation</li>
</ol>
<p><strong>Error handling in tool results:</strong> When a tool execution fails, set <code>&quot;is_error&quot;: true</code> and provide an informative error message. Claude will typically acknowledge the error and either try a different approach or ask for clarification.</p>
<p><strong>Multiple tool calls:</strong> Claude can request multiple tools in a single response. Handle them all before continuing — send all results back in a single <code>user</code> message.</p>
<hr />
<h2>Server-Side Tools: Code Execution</h2>
<p>The code execution tool lets Claude run code in a secure, sandboxed container. Unlike user-defined tools, server-side tools run on Anthropic's infrastructure — you don't execute anything client-side. Just include the tool definition and Claude handles the rest.</p>
<h3>Key Facts</h3>
<ul>
<li>Runs in an isolated container (1 CPU, 5 GiB RAM, 5 GiB disk)</li>
<li>No internet access (fully sandboxed)</li>
<li>Python 3.11 with data science libraries pre-installed</li>
<li>Containers persist for 30 days and can be reused across requests</li>
<li>Free when used with web search/web fetch tools; otherwise $0.05/hour after 1,550 free hours/month per organization</li>
</ul>
<h3>Tool Definition</h3>
<p>The tool requires no schema — just declare it in the <code>tools</code> array:</p>
<pre><code class="language-json">{
  &quot;type&quot;: &quot;code_execution_20260120&quot;,
  &quot;name&quot;: &quot;code_execution&quot;
}
</code></pre>
<p>Claude automatically gains access to <code>bash_code_execution</code> (run shell commands) and <code>text_editor_code_execution</code> (create/view/edit files).</p>
<h3>Pre-installed Python Libraries</h3>
<ul>
<li><strong>Data science</strong>: pandas, numpy, scipy, scikit-learn, statsmodels</li>
<li><strong>Visualization</strong>: matplotlib, seaborn</li>
<li><strong>File processing</strong>: openpyxl, xlsxwriter, pillow, pypdf, pdfplumber, python-docx, python-pptx</li>
<li><strong>Math</strong>: sympy, mpmath</li>
<li><strong>Utilities</strong>: tqdm, python-dateutil, pytz, sqlite3</li>
</ul>
<p>Additional packages can be installed at runtime via <code>pip install</code>.</p>

<h3>Container Reuse</h3>
<p>Reuse containers across requests to maintain state (files, installed packages, variables). Extract the <code>container_id</code> from the first response and pass it to subsequent requests.</p>
<h3>Response Structure</h3>
<p>The response contains interleaved text and tool result blocks:</p>
<ul>
<li><code>text</code> — Claude's explanation</li>
<li><code>server_tool_use</code> — What Claude is doing</li>
<li><code>bash_code_execution_tool_result</code> — Code execution output (check <code>return_code</code> for success/failure)</li>
<li><code>text_editor_code_execution_tool_result</code> — File operation results</li>
</ul>
<blockquote>
<p><strong>Security:</strong> Always sanitize filenames with <code>os.path.basename()</code> / <code>path.basename()</code> before writing downloaded files to disk to prevent path traversal attacks. Write files to a dedicated output directory.</p>
</blockquote>

<h2>Server-Side Tools: Web Search and Web Fetch</h2>

<h3>Dynamic Filtering (Opus 4.6 / Sonnet 4.6)</h3>
<p>The <code>web_search_20260209</code> and <code>web_fetch_20260209</code> versions support <strong>dynamic filtering</strong> — Claude writes and executes code to filter search results before they reach the context window, improving accuracy and token efficiency. Dynamic filtering requires:</p>
<ol>
<li>The code execution tool (<code>code_execution_20260120</code>) must also be enabled in <code>tools</code></li>
<li>The beta header <code>code-execution-web-tools-2026-02-09</code></li>
</ol>
<p>Header: <code>anthropic-beta: code-execution-web-tools-2026-02-09</code></p>
<pre><code class="language-json">{

    { &quot;type&quot;: &quot;web_search_20260209&quot;, &quot;name&quot;: &quot;web_search&quot; },

<h2>Structured Outputs</h2>
<p>Structured outputs constrain Claude's responses to follow a specific JSON schema, guaranteeing valid, parseable output. This is not a separate tool — it enhances the Messages API response format and/or tool parameter validation.</p>
<p>Two features are available:</p>
<ul>
<li><strong>JSON outputs</strong> (<code>output_config.format</code>): Control Claude's response format</li>
<li><strong>Strict tool use</strong> (<code>strict: true</code>): Guarantee valid tool parameter schemas</li>
</ul>
<p><strong>Supported models:</strong> Claude Opus 4.6, Claude Sonnet 4.6, and Claude Haiku 4.5. Legacy models (Claude Opus 4.5, Claude Opus 4.1) also support structured outputs.</p>
<blockquote>
<p><strong>Recommended:</strong> Use <code>client.messages.parse()</code> which automatically validates responses against your schema. When using <code>messages.create()</code> directly, use <code>output_config: {format: {...}}</code>. The <code>output_format</code> convenience parameter is also accepted by some SDK methods (e.g., <code>.parse()</code>), but <code>output_config.format</code> is the canonical API-level parameter.</p>
</blockquote>
<h3>JSON Schema Limitations</h3>
<p><strong>Supported:</strong></p>
<ul>
<li>Basic types: object, array, string, integer, number, boolean, null</li>
<li><code>enum</code>, <code>const</code>, <code>anyOf</code>, <code>allOf</code>, <code>$ref</code>/<code>$def</code></li>
<li>String formats: <code>date-time</code>, <code>time</code>, <code>date</code>, <code>duration</code>, <code>email</code>, <code>hostname</code>, <code>uri</code>, <code>ipv4</code>, <code>ipv6</code>, <code>uuid</code></li>
<li><code>additionalProperties: false</code> (required for all objects)</li>
</ul>
<p><strong>Not supported:</strong></p>
<ul>
<li>Recursive schemas</li>
<li>Numerical constraints (<code>minimum</code>, <code>maximum</code>, <code>multipleOf</code>)</li>
<li>String constraints (<code>minLength</code>, <code>maxLength</code>)</li>
<li>Complex array constraints</li>
<li><code>additionalProperties</code> set to anything other than <code>false</code></li>
</ul>
<p>The Python and TypeScript SDKs automatically handle unsupported constraints by removing them from the schema sent to the API and validating them client-side.</p>
<h3>Important Notes</h3>
<ul>
<li><strong>First request latency</strong>: New schemas incur a one-time compilation cost. Subsequent requests with the same schema use a 24-hour cache.</li>
<li><strong>Refusals</strong>: If Claude refuses for safety reasons (<code>stop_reason: &quot;refusal&quot;</code>), the output may not match your schema.</li>
<li><strong>Token limits</strong>: If <code>stop_reason: &quot;max_tokens&quot;</code>, output may be incomplete. Increase <code>max_tokens</code>.</li>
<li><strong>Incompatible with</strong>: Citations (returns 400 error), message prefilling.</li>
<li><strong>Works with</strong>: Batches API, streaming, token counting, extended thinking.</li>
</ul>
<hr />
<h2>Tips for Effective Tool Use</h2>
<ol>
<li><strong>Provide detailed descriptions</strong>: Claude relies heavily on descriptions to understand when and how to use tools</li>
<li><strong>Use specific tool names</strong>: <code>get_current_weather</code> is better than <code>weather</code></li>
<li><strong>Validate inputs</strong>: Always validate tool inputs before execution</li>
<li><strong>Handle errors gracefully</strong>: Return informative error messages so Claude can adapt</li>
<li><strong>Limit tool count</strong>: Too many tools can confuse the model — keep the set focused</li>
<li><strong>Test tool interactions</strong>: Verify Claude uses tools correctly in various scenarios</li>
</ol>
<p>For detailed tool use documentation, use WebFetch:</p>
<ul>
<li>URL: <code>https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview</code></li>
</ul>

<h1>Message Batches API — TypeScript</h1>
<p>The Batches API (<code>POST /v1/messages/batches</code>) processes Messages API requests asynchronously at 50% of standard prices.</p>
<h2>Key Facts</h2>

<li>Most batches complete within 1 hour; maximum 24 hours</li>
<li>Results available for 29 days after creation</li>
<li>50% cost reduction on all token usage</li>
<li>All Messages API features supported (vision, tools, caching, etc.)</li>

<h2>Streaming with Tool Use (Tool Runner)</h2>
<p>Use the tool runner with <code>stream: true</code>. The outer loop iterates over tool runner iterations (messages), the inner loop processes stream events:</p>
<pre><code class="language-typescript">import Anthropic from &quot;@anthropic-ai/sdk&quot;;
import { betaZodTool } from &quot;@anthropic-ai/sdk/helpers/beta/zod&quot;;
import { z } from &quot;zod&quot;;

const client = new Anthropic();

const getWeather = betaZodTool({
  name: &quot;get_weather&quot;,
  description: &quot;Get current weather for a location&quot;,
  inputSchema: z.object({
    location: z.string().describe(&quot;City and state, e.g., San Francisco, CA&quot;),
  }),
  run: async ({ location }) =&gt; `72°F and sunny in ${location}`,
});

const runner = client.beta.messages.toolRunner({
  model: &quot;claude-opus-4-6&quot;,
  max_tokens: 4096,
  tools: [getWeather],
  messages: [
    { role: &quot;user&quot;, content: &quot;What's the weather in Paris and London?&quot; },
  ],
  stream: true,
});

// Outer loop: each tool runner iteration
for await (const messageStream of runner) {
  // Inner loop: stream events for this iteration
  for await (const event of messageStream) {
    switch (event.type) {
      case &quot;content_block_delta&quot;:
        switch (event.delta.type) {
          case &quot;text_delta&quot;:
            process.stdout.write(event.delta.text);
            break;
          case &quot;input_json_delta&quot;:
            // Tool input being streamed
            break;
        }
        break;
    }
  }
}
</code></pre>
<hr />
<h2>Getting the Final Message</h2>
<pre><code class="language-typescript">const stream = client.messages.stream({
  model: &quot;claude-opus-4-6&quot;,
  max_tokens: 1024,
  messages: [{ role: &quot;user&quot;, content: &quot;Hello&quot; }],

for await (const event of stream) {
  // Process events...

<h2>Stream Event Types</h2>
<table>
<thead>
<tr><th>Event Type</th><th>Description</th><th>When it fires</th></tr>
</thead>
<tbody>
<tr><td><code>message_start</code></td><td>Contains message metadata</td><td>Once at the beginning</td></tr>
<tr><td><code>content_block_start</code></td><td>New content block beginning</td><td>When a text/tool_use block starts</td></tr>
<tr><td><code>content_block_delta</code></td><td>Incremental content update</td><td>For each token/chunk</td></tr>
<tr><td><code>content_block_stop</code></td><td>Content block complete</td><td>When a block finishes</td></tr>
<tr><td><code>message_delta</code></td><td>Message-level updates</td><td>Contains <code>stop_reason</code>, usage</td></tr>

</tbody>
</table>
<h2>Best Practices</h2>
<ol>
<li><strong>Always flush output</strong> — Use <code>process.stdout.write()</code> for immediate display</li>
<li><strong>Handle partial responses</strong> — If the stream is interrupted, you may have incomplete content</li>
<li><strong>Track token usage</strong> — The <code>message_delta</code> event contains usage information</li>
<li><strong>Use <code>finalMessage()</code></strong> — Get the complete response even when streaming for timeout protection</li>
<li><strong>Buffer for web UIs</strong> — Consider buffering a few tokens before rendering to avoid excessive DOM updates</li>
</ol>

<h2>Tool Runner (Recommended)</h2>
<p><strong>Beta:</strong> The tool runner is in beta in the TypeScript SDK.</p>
<p>Use <code>betaZodTool</code> with Zod schemas to define tools with a <code>run</code> function, then pass them to <code>client.beta.messages.toolRunner()</code>:</p>

  description: &quot;Get current weather for a location&quot;,

    unit: z.enum([&quot;celsius&quot;, &quot;fahrenheit&quot;]).optional(),
  }),

    // Your implementation here

  },

<p><strong>Key benefits of the tool runner:</strong></p>
<ul>
<li>No manual loop — the SDK handles calling tools and feeding results back</li>
<li>Type-safe tool inputs via Zod schemas</li>
<li>Tool schemas are generated automatically from Zod definitions</li>
